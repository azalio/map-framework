# MAP Framework: Улучшения на основе контекстной инженерии

> **Источник:** Анализ статьи "Context Engineering for AI Agents with LangChain" и отчета context-engenering.pdf
> **Дата:** 2025-10-18
> **Статус:** Планирование и реализация

## 📖 Введение

Данный документ содержит комплексный план улучшений MAP Framework на основе принципов контекстной инженерии, описанных в статье "Context Engineering for AI Agents: Lessons from Building Manus" и адаптированных для MAP Framework в отчете context-engenering.pdf.

MAP Framework уже реализует многие передовые практики:
- ✅ Модульная архитектура с 9 специализированными агентами
- ✅ ACE (Adaptive Contextual Engine) для обучения на опыте
- ✅ Семантический поиск по базе знаний
- ✅ Оптимизация стоимости через распределение моделей (haiku/sonnet/opus)
- ✅ Интеграция с MCP-серверами для внешней памяти

Однако анализ выявил несколько областей для дальнейшего совершенствования.

## 🎯 Ключевые принципы контекстной инженерии

### 1. Стабильность префикса и KV-кэш
**Принцип:** Промпт-префикс должен быть неизменным; контекст обновлять только дописыванием (append-only).

**Текущее состояние в MAP:**
- ✅ Шаблоны агентов хранятся в `.claude/agents/*.md` с placeholders
- ✅ Pre-commit хуки защищают критические переменные
- ⚠️ Нет строгого контроля append-only политики для истории диалога

**Рекомендации:**
- [ ] Гарантировать append-only добавление результатов агентов
- [ ] Не редактировать ранее сгенерированные сообщения в контексте
- [ ] Оркестратор должен только добавлять новые шаги, не переписывая историю

### 2. Фиксированный набор агентов
**Принцип:** Не менять состав инструментов/агентов во время выполнения без крайней необходимости.

**Текущее состояние в MAP:**
- ✅ Набор из 9 агентов фиксирован и задан заранее
- ⚠️ Нет механизма маскирования для временного отключения агентов

**Рекомендации:**
- [ ] Реализовать флаги доступности агентов вместо удаления описаний
- [ ] Оркестратор сигнализирует, какие агенты уместны, но все описания остаются в контексте
- [ ] Это сохранит KV-кэш при необходимости настройки состава

### 3. Внешнее хранилище как расширение контекста
**Принцип:** Файловая система как безграничный контекст — модель записывает важные данные во внешние файлы и читает по мере надобности.

**Текущее состояние в MAP:**
- ✅ Интеграция с MCP-серверами (cipher, deepwiki, context7)
- ✅ Playbook хранится в `.claude/playbook.json`
- ⚠️ Нет механизма сохранения промежуточных артефактов на диск

**Рекомендации:**
- [ ] Оркестратор создает файл планирования (`.map/current_plan.md`)
- [ ] Агенты сохраняют большие данные в `.map/artifacts/`
- [ ] В контексте хранятся только ссылки или краткие аннотации

### 4. Фокусировка внимания (Recitation)
**Принцип:** Периодически повторять главные цели в конце контекста, чтобы держать их "свежими".

**Текущее состояние в MAP:**
- ⚠️ Нет механизма Recitation
- ⚠️ На длинных задачах модель может "терять нить"

**Рекомендации:**
- [ ] **Критично:** Оркестратор поддерживает `.map/current_plan.md`
- [ ] Перед каждой подзадачей обновленный список целей добавляется в контекст
- [ ] Actor видит актуальный "маяк" целей в недавних токенах
- [ ] Формат: текущая подзадача, выполненные шаги, осталось сделать

**Пример `.map/current_plan.md`:**
```markdown
# Current Task: Implement user authentication

## Overall Goal
Implement JWT-based authentication with email/password

## Subtasks
- [x] 1/5: Create User model with password hashing
- [x] 2/5: Implement login endpoint
- [→] 3/5: Add JWT token generation (CURRENT)
- [ ] 4/5: Implement token validation middleware
- [ ] 5/5: Add refresh token mechanism

## Current Focus
Generating JWT tokens with expiration, using HS256 algorithm
```

### 5. Ошибки как обучающая информация
**Принцип:** "Keep the wrong stuff in" — не удалять ошибки из контекста, они помогают модели учиться.

**Текущее состояние в MAP:**
- ✅ Monitor передает feedback Actor'у через `{{#if feedback}}`
- ✅ Ошибки сохраняются в истории диалога
- ✅ Соответствует рекомендации статьи

**Рекомендации:**
- [x] Текущая реализация корректна
- [ ] Убедиться, что хуки не очищают контекст от ошибок

### 6. Избежание few-shot bias
**Принцип:** Модели склонны имитировать образцы. Слишком много однотипных примеров приводит к шаблонному поведению.

**Текущее состояние в MAP:**
- ✅ Curator отфильтровывает дубликаты (>90% similarity)
- ⚠️ Подсказки из playbook могут быть однообразными

**Рекомендации:**
- [ ] Варьировать формулировки подсказок из базы знаний
- [ ] Если нашлось 3 паттерна: один как псевдокод, другой как совет, третий как документация
- [ ] Оркестратор меняет формулировку задач для Actor (не всегда "Реализуй функцию X")

## 📊 Память и retrieval стратегии

### Оптимизация извлечения (Retrieval)
**Текущее состояние:**
- ✅ Семантический поиск с `all-MiniLM-L6-v2`
- ✅ Кеширование эмбеддингов
- ⚠️ Количество извлекаемых паттернов не ограничено

**Рекомендации:**
- [ ] **Критично:** Ограничить до 3-5 самых релевантных bullets
- [ ] Слишком много паттернов → context distraction
- [ ] Комбинировать keyword + semantic поиск для повышения точности

### Размер и сегментация паттернов
**Рекомендации:**
- [ ] Каждый паттерн в playbook должен быть коротким (помещаться целиком)
- [ ] Объемные паттерны (длинный код) → отдельный файл в `docs/playbook/patterns/`
- [ ] В playbook хранить только ссылку и краткую аннотацию

### Chunking внешних данных
**Рекомендации:**
- [ ] `context7` и `deepwiki` должны использовать разбиение на фрагменты
- [ ] Retriever возвращает только подходящие части, не весь документ
- [ ] Рассмотреть заимствование LangChain Document Loaders для PDF/HTML/кода

## ⚡ Производительность и экономия токенов

### KV-cache hit rate
**Рекомендации:**
- [ ] Убедиться, что Actor-Monitor-... выполняются в одной сессии Claude
- [ ] Один conversation ID для всех связанных вызовов

### Снижение latency
**Рекомендации:**
- [ ] **Критично:** Reflector/Curator запускать асинхронно (в фоне)
- [ ] Они обновляют knowledge base, не влияя на основной контекст
- [ ] Пользователь получает результат быстрее

### Оптимизация объема контекста
**Рекомендации:**
- [ ] **Критично:** Monitor пишет лаконичные метки вместо развернутых отзывов
- [ ] При повторном запуске Actor не перечислять все выполненные шаги
- [ ] Каждый агент получает только необходимую информацию
- [ ] Evaluator'у не нужно исходное описание задачи — только код и требования

### Кэширование результатов инструментов
**Рекомендации:**
- [ ] Если `context7` запросил документацию Stripe → сохранить в `.map/cache/stripe_docs.md`

### Мониторинг и профилирование
**Рекомендации:**
- [ ] Собирать метрики: токены по агентам, время каждого шага

- [ ] Сохранять в `.map/metrics/usage_TIMESTAMP.json`
- [ ] Анализ показывает узкие места для оптимизации

## 🔗 Интеграция с LangChain/LangGraph (Опционально)

### Multi-Action Agents
**Идея:** LangChain позволяет агенту выполнить несколько действий за один шаг.
**Для MAP:** Можно объединять простые подзадачи, если модель это "планирует".

### LangGraph и графы состояний
**Идея:** Представить MAP как граф выполнения (узлы=агенты, ребра=переходы).
**Для MAP:** Использовать идею "sub-agent isolation" — Reflector/Curator асинхронно.

### Memory и Tool abstraction
**Идея:** Унифицированный интерфейс для инструментов и памяти.
**Для MAP:**
- [ ] Создать адаптер: expose `mapify_cli.playbook_manager.search` как LangChain Tool
- [ ] Позволит использовать MAP-модуль в других LLM-агентах
- [ ] Или подключать LangChain инструменты внутри MAP (веб-поиск через SerpAPI)

### Document Loaders
**Идея:** LangChain имеет готовые загрузчики для PDF, HTML, кода.
**Для MAP:** Использовать для chunking внешних данных от `deepwiki`/`context7`.

## 📈 Метрики успеха

### До улучшений (baseline)
- Monitor approval rate: ~80% первая попытка
- Evaluator scores: средний ~7.0/10
- Iteration count: ~3 на подзадачу
- Cost per 5-subtask feature: ~$0.35

### После улучшений (цели)
- **Качество:** Monitor approval rate → 90-95% (за счет фокусировки и лучших паттернов)
- **Производительность:** -30-40% времени на длинных задачах (кеширование, параллелизм)
- **Стоимость:** -10-15% токенов (оптимизация verbose, ограничение паттернов)
- **Надежность:** +50% воспроизводимость (логи, checkpoints)
- **Iteration count:** ~2 на подзадачу (меньше ретраев)
